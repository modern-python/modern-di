# Design: Optional open() and monotonicity-split validation

## Summary

`open()` stops being mandatory. A constructed container is usable immediately:
the first `resolve` / `resolve_provider` prepares it (runs any pending
validation, clears `closed`). Reuse after an explicit close self-reopens and
emits `ContainerClosedWarning`, restoring the 2.x behavior that 3.0 turned into
`ContainerClosedError`. `build_child_container` drops its openness requirement
entirely. Validation splits by monotonicity: cycles and inverted scopes raise
from `Container(...)`, while missing dependencies and dangling aliases are held
on the shared providers registry and raised at first use. `open()` and
`with`/`async with` keep their exact meaning and stay the recommended form.
Ships as **3.1.0**, a pure relaxation: every 3.0 pattern keeps working and no
integration needs a code change.

## Motivation

3.0 (tagged 2026-07-20) tightened two knobs at once:
[.20](2026-07-19.20-mandatory-open-lifecycle.md) made `open()` mandatory and
[.19](2026-07-19.19-validate-by-default-deferred.md) made `open()` the sole
validation trigger. Six days of field evidence says the tightening cost more
than it bought. [2026-07-21.01](2026-07-21.01-integration-open-lifecycle-lessons.md)
records six production defects, all one root cause (the root's open hook does
not fire in some execution context, so the first unit of work raises), plus an
authoring rule that exists only because validation is bound to `open()`: open
the root *after* `setup_di`, or a by-type dependency on a not-yet-registered
connection fails validation. Both classes are unfixable in integration code
(ruled inherent in [d3-root-lifecycle-inherent](../decisions/2026-07-25-d3-root-lifecycle-inherent.md)),
because they are consequences of the core contract, not of the adapters.

Two properties make the relaxation cheap. First, a closed container is already
mechanically fresh: `CacheItem._clear()` evicts the instance and resets
`finalized` under the default `clear_cache=True`, so reopening is a flag flip
with nothing to repair. Second, the checks `validate()` runs are not equal.
Registering more providers can only ever *add* a cycle or an inverted scope,
never remove one (a missing dependency contributes no edge, and a dangling
`Alias` falls back to its own scope), so those two checks cannot produce a false
positive on an incomplete graph. Only completeness is non-monotone, and it is
the sole reason validation was deferred in the first place.

## Design

**Lifecycle.** Three states over the public `closed: bool` plus a private
`_ever_closed: bool`, set in `close_sync` / `close_async` and never reset:

| State | `closed` | `_ever_closed` | Implicit use | `open()` / `with` |
|---|---|---|---|---|
| New | `True` | `False` | prepares silently | prepares, silent |
| Open | `False` | either | proceeds | re-runs held validation; otherwise no-op |
| Closed | `True` | `True` | prepares, warns | prepares, silent |

The discriminator is *has this container been closed*, not *has it been
opened*: a container constructed, closed, then used belongs in the Closed row,
because the user called `close_sync()` on it. `_prepare()` runs on the slow
path only: warn when `_ever_closed`, run pending validation when still pending,
then set `closed = False`. It takes the container's `_lock` when
`use_lock=True` and is idempotent under a race (the walk is pure, and the flag
write happens last). `open()` calls the same preparation directly, skipping the
warning, so a deliberate reopen is silent.

`build_child_container` loses `_raise_if_closed()`: it reads `_scope_map` and
the two shared registries, resolves nothing, and touches no cache, so a closed
parent is irrelevant to it. The warning then fires exactly when a closed
container is used to hold or resolve state, never when it merely parents a
child.

**Validation.** `__init__` (root, `validate=True`) runs one
`DependencyGraph().walk`. `Cycle` and inverted-`Edge` errors raise
`ValidationFailedError` from the constructor. `NodeEntered` /
`DependenciesError` errors are stored as pending on **`ProvidersRegistry`**,
which is shared tree-wide, so a child's first use raises them too and no
child-only path can skip validation (this replaces the build-guard argument in
`architecture/containers.md:90-99`). The first `_prepare()` raises the pending
list if the registry has not mutated since, and re-walks if `add_providers` ran
in between.

All three pieces of validation state therefore live on the registry, not the
container: the enabled bit (written once by the root that creates the registry,
from its `validate` argument), the pending completeness errors, and the
existing `_validated` flag. A child preparing before its root has all it needs
to decide whether to re-walk, and whichever container completes a walk marks
the registry validated for the whole tree. The container keeps
`_validate_enabled` only to decide whether `__init__` walks at all; its
per-container `_validated` flag loses its last reader and is deleted.

`add_providers` follows the same rule and keeps its atomic rollback, with one
consequence worth stating: a completeness error that 3.0 raised from
`add_providers` now defers to first use. That is what keeps two-batch
registration working, where one batch depends on the next.
`container.validate()` is unchanged: a full walk raising both classes.
`validate=False` still means nothing implicit.

Two consequences: the "open the root after `setup_di`" authoring rule narrows,
rather than dissolves — it stops applying to callers who rely on implicit
first-use preparation (always after registration), but still binds a caller
that calls `open()` explicitly, since `open()` runs `_ensure_ready()`
unconditionally and still raises a completeness error the registry is holding;
and the registry's acyclic-known flag is now set at construction, so
`resolve_provider`'s `RecursionError` guard short-circuits from the start.

**Hot path.** Compiled resolvers keep `if target.closed:`
(`resolver_compiler.py:100,127,221,263`), the same single branch they emit
today; only the body changes from `_raise_if_closed()` to `_prepare()`. After
first touch `closed` is `False`, so steady-state resolve cost is unchanged, and
no per-resolve validation check returns.

**Error surface.** `ContainerClosedWarning` is revived with its 2.x role, its
message rendered in `exceptions.py` from a `container_scope` attr per that
file's rule, and re-based from `DeprecationWarning` to `RuntimeWarning`:
CPython hides deprecation warnings outside `__main__`, which would hide this
diagnostic from exactly the applications that need it.
`ContainerClosedError` loses its only raise site
(`container.py:341`) and stays importable, documented and deprecated for 3.x,
removed in 4.0: the mirror of what 3.0 did to the warning. Its troubleshooting
page stays (the census test pins a bijection) and is rewritten.

## Non-goals

- No strict mode or opt-in error flag: reuse-after-close is warn-only, and an
  explicit `open()` is how a deliberate reuse is silenced.
- No rename of `closed` (a never-opened container still reports `closed=True`
  while usable). That wart predates this change; `is_open` is a 4.0 item.
- No change to what `validate()` checks, only to when each class is raised.
- No integration code changes: every current `open()` / `with` call stays
  correct.

## Testing

`just test-ci` (100% line coverage) and `just lint-ci` clean; `mkdocs build
--strict` clean. Each behavior gets a failing test first.

New: fresh container resolves with no `open()` and no warning; fresh parent to
child to resolve with neither opened; cycle raises from `Container(...)`;
missing dependency does not raise at construction but does at first resolve;
the `add_providers`-after-construction integration pattern validates clean at
first use; reuse-after-close warns and rebuilds; explicit `open()` after close
is silent; a child built off a closed parent is silent, but resolving an
APP-scoped provider through it warns; `validate=False` walks nothing;
a monotone error from `add_providers` still rolls back atomically; two threads
racing first touch validate exactly once; `ContainerClosedError` stays
importable and constructible (back-compat pin and coverage).

Flipped: roughly 17 `ContainerClosedError` assertions in
`tests/test_container.py` plus references in
`tests/providers/{test_factory,test_singleton,test_context_provider}.py` move
from "raises" to "works". The ~196 sites wrapped for 3.0 stay valid.

Benchmarks: the G8 cold scenario measures construction, which now carries the
monotone walk when validation is on. Measured with the validate benchmarks from
[2026-07-19.05](2026-07-19.05-validate-benchmarks.md) and the delta reported
here at ship, not assumed.

## Risk

- **Startup cost moves and, for integrations, doubles.** A plain user pays one
  walk (construction); an integration that calls `add_providers` pays two
  (construction plus first use) where 3.0 paid one. Startup-only, and the
  alternative (two walk modes) costs everyone two. Reported from benchmarks at
  ship.
- **Errors move earlier.** A cycle that surfaced at `open()` now raises from
  `Container(...)`. Same exception class, earlier frame. Intended, and noted in
  the 3.1 release notes and a `docs/migration/to-3.x.md` addendum.
- **A leaked reference is now a warning, not an error.** A child captured past
  its request rebuilds objects nobody will finalize. The warning is the
  detector; `-W error` promotes it for those who want 3.0's strictness.
- **Docs churn across an already-published 3.0 story.** `architecture/`
  (containers, validation, concurrency), the four per-integration deployment
  caveats (whose failure mode softens from "every unit of work raises" to "the
  root never closes, so finalizers do not run"), and
  `docs/integrations/writing-integrations.md` lifecycle rules (rule 1, "open the
  root after `setup_di`", narrows to the explicit-`open()` case only; rule 2
  softens to fail-fast plus finalizers). 3.0's migration history is amended, not rewritten, and
  [d3-root-lifecycle-inherent](../decisions/2026-07-25-d3-root-lifecycle-inherent.md)
  gets an amendment note: its revisit trigger has fired, though its conclusion
  (no integration code changes) still holds, since none are needed.
