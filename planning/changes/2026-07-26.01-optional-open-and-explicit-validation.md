# Design: Optional open() and explicit-only validation

## Summary

Two knobs 3.0 tightened are relaxed. **Lifecycle:** a constructed container is
open; `open()` stops being mandatory, and reusing an explicitly closed container
emits `ContainerClosedWarning` and reopens instead of raising
`ContainerClosedError`. **Validation:** `container.validate()` becomes the only
trigger. Neither `__init__` nor `open()` nor `add_providers` nor a resolve ever
validates, so the `validate` constructor argument has nothing left to gate and
becomes a deprecated no-op (removed in 4.0). `open()` and `with` / `async with`
keep their spelling and stay the recommended form. Ships as **3.1.0**; every
3.0 pattern keeps working and no integration needs a code change.

## Motivation

3.0 (tagged 2026-07-20) made `open()` mandatory
([.20](2026-07-19.20-mandatory-open-lifecycle.md)) and made it the sole
validation trigger ([.19](2026-07-19.19-validate-by-default-deferred.md)).
[2026-07-21.01](2026-07-21.01-integration-open-lifecycle-lessons.md) records six
production defects from the first, all one root cause: the root's open hook does
not fire in some execution context, so the first unit of work raises. The second
produced an authoring rule that exists only because validation is bound to
`open()`: open the root *after* `setup_di`, or a by-type dependency on a
not-yet-registered connection fails validation.

An earlier revision of this design kept validation implicit by splitting it in
two: cycles and inverted scopes eagerly at construction (they are monotone, since
registering more providers can only ever *add* such an error), and completeness
held on the shared registry and raised at first use. It worked, but the machinery
it needed was out of proportion to what it bought — a two-flag container
lifecycle so a fresh container could be told from a closed one, validation state
parked on `ProvidersRegistry`, a monotone/completeness classification threaded
through the graph walk, and an `add_providers` rollback path. Keeping the
implicit guarantee *without* that machinery requires a per-resolve check, which
taxes the hot path for a startup-time concern. Maintainer ruling: make the
trigger explicit and predictable instead. `validate()` is one call, it reports
every wiring bug at once, and nothing about when it runs has to be inferred.

A closed container is already mechanically fresh, which is what makes the
lifecycle half cheap: `CacheItem._clear()` evicts the instance and resets
`finalized` under the default `clear_cache=True`, so reopening is a flag flip
with nothing to repair.

## Design

**Lifecycle — two states.** `__init__` sets `closed = False`: a container is open
the moment it exists. `close_sync` / `close_async` run finalizers and set
`closed = True`. An implicit use of a closed container (`resolve`,
`resolve_provider`, or a compiled resolver navigating to it) emits
`ContainerClosedWarning`, reopens, and proceeds; `open()` reopens silently, which
is how a deliberate reuse is expressed. `build_child_container` requires nothing
of its parent: it reads `_scope_map` and the two shared registries, resolves
nothing, and touches no cache.

`_prepare()` is the slow-path entry: under the container's `_lock` it re-checks
`closed` (so a racing second thread neither double-warns nor double-opens), warns,
then clears the flag. The warning's `stacklevel` is computed by walking out of the
package (`_caller_stacklevel`), because compiled resolvers recurse to variable
depth and no fixed level can name the caller.

**Hot path unchanged.** Compiled resolvers keep the single `if target.closed:`
test they emit today, with only the body calling `_prepare()`. An open container
fails that test, so steady-state resolve cost is untouched, and no per-resolve
validation check exists.

**Validation — explicit only.** `container.validate()` walks the graph once,
collects cycles, inverted scopes, missing dependencies and dangling aliases, and
raises one aggregated `ValidationFailedError`. Nothing else calls it.
`ProvidersRegistry` keeps its `_validated` flag, which memoizes a clean walk and
is cleared by every mutation; it also short-circuits `resolve_provider`'s
`RecursionError` guard. It loses the enabled bit and the pending-error store.

`add_providers` registers and nothing more: no re-validation, no batch rollback.
The mutation clears `_validated`, so the next explicit `validate()` re-walks.

`Container(validate=...)` is accepted, ignored, and warned about with a
`DeprecationWarning` naming `validate()` as the replacement; the parameter is
removed in 4.0. Keeping it accepted matters because 3.0 callers pass
`validate=False` widely, including this repo's own benchmark guards.

## Non-goals

- No strict mode: reuse-after-close is warn-only; an explicit `open()` silences it.
- No rename of `closed` to `is_open`; that stays a 4.0 item.
- No change to *what* `validate()` checks, only to when it runs.
- No integration code changes; integrations wanting boot-time fail-fast call
  `validate()` after registering their providers.

## Testing

- `just test-ci`: **437 passed, 100.00% line coverage** (2 pre-existing,
  unrelated `UserWarning`s from `test_types_parser.py`). `just lint-ci`
  (`eof-fixer`, `ruff format --check`, `ruff check`, `ty check`,
  `planning/index.py --check`) and `just check-planning`: clean. `uvx
  --with-requirements docs/requirements.txt mkdocs build --strict`: clean.
- Behavior pinned in `tests/test_container.py` /
  `tests/test_free_threading.py`: a constructed container resolves with no
  `open()` and no warning; reuse after an explicit close warns once and
  reopens, while an explicit `open()` after close is silent; N threads racing
  a closed container record exactly one `ContainerClosedWarning`;
  `build_child_container` off a closed parent is silent; `__init__`, `open()`
  and `add_providers` never validate; `validate=` (either value) emits
  `ValidateArgumentWarning` and changes nothing, while omitting it is silent;
  `validate()` still aggregates every error class in one
  `ValidationFailedError`, and still suppresses a dangling-alias scope
  inversion (`tests/providers/test_alias.py`), reporting
  `AliasSourceNotRegisteredError` instead.
- `just bench`, this branch vs. `main` (ff51ee6) in a scratch `git worktree`,
  same machine, same run: the **resolve tier is unchanged**, as expected —
  compiled resolvers keep the identical single `if target.closed:` test per
  code path (4 call sites in `resolver_compiler.py`, unchanged count on both
  branches), with only the body swapped (`_prepare()` vs. `_raise_if_closed()`).
  Guard-tier medians move within ordinary run-to-run noise: `test_g2_cached_resolve`
  178.3 ns (branch) vs. 193.3 ns (main); `test_g1_transient_resolve` 334.0 ns vs.
  375.0 ns; `test_g3_deep_chain` 834.0 ns vs. 875.0 ns; `test_g8_cold_first_resolve`
  (both run with implicit validation off) 14.58 µs vs. 14.67 µs. **Construction is
  cheaper**, as expected — `main` (3.0) runs its default `validate=True` graph
  walk at `open()`; this branch never validates implicitly. An ad hoc,
  uncommitted `pytest-benchmark` scenario (the shape once existed on this
  branch as G16, deleted once the split-validation design it measured was
  itself discarded — see Design above) timing `Container(scope=Scope.APP,
  groups=[ChainGroup]); container.open()` with default arguments, depth-6
  chain: **~2.6 µs median (branch) vs. ~15.5 µs median (main)**, matching the
  `test_g10_validate_deep_chain` guard cost (~13–17 µs) that `main`'s `open()`
  pays and this branch's does not.

## Risk

- **The default safety posture drops, silently.** A broken graph previously
  raised at `open()`; now it surfaces only from an explicit `validate()`, or as a
  resolve-time `ArgumentResolutionError` when the unwireable provider is actually
  resolved. Nothing that worked breaks, but a user who believed the default
  protected them loses that. The `validate=` deprecation warning is the signal,
  and the release notes and integration docs carry the replacement idiom.
- **`add_providers` is no longer atomic against a validated graph.** A batch that
  breaks the graph registers quietly and surfaces at the next `validate()`.
- **Docs churn across an already-published 3.0 story**: `architecture/`
  (containers, validation, concurrency), the integration lifecycle rules, the four
  per-integration deployment caveats, and the migration record. 3.0's history is
  amended, never rewritten.
