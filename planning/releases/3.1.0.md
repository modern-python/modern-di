# modern-di 3.1.0 — open() becomes optional

3.1 relaxes the headline 3.0 change: a container no longer has to be opened
before use. Every 3.0 pattern (`with`, `async with`, `open()`) keeps working
exactly as documented — this is a pure relaxation, not a reversal, and no
integration needs a code change.

## Feature

- **A constructed container is usable immediately.** `Container(...)`
  is ready to resolve from as soon as it returns — the first `resolve` /
  `resolve_provider` prepares it (runs any deferred validation, clears
  `closed`), with no warning. `open()` and `with`/`async with` are unchanged
  in spelling and stay the recommended form for fail-fast startup and for
  running finalizers on the way out; `open()` still runs its checks
  unconditionally, so it's the verb to reach for when you want validation to
  fail before the first real request does. `build_child_container` no longer
  requires anything of its parent's open state either.

- **Reusing a closed container warns instead of raising.** Resolving
  from — or building a child of — a container after an explicit `close_sync`/
  `close_async` now emits `ContainerClosedWarning` and reopens it, restoring
  the 2.x self-healing behavior that 3.0 turned into a hard
  `ContainerClosedError`. An explicit `open()` after a close stays silent — it's
  how you tell modern-di the reuse is deliberate. `ContainerClosedWarning` is a
  `RuntimeWarning`, not a `DeprecationWarning` as it was pre-3.0: CPython hides
  deprecation warnings outside `__main__`, which would hide this diagnostic
  from exactly the long-running services that need to see it.

- **Cycles and inverted scopes now surface at construction.** Validation
  splits by whether registering more providers could ever remove the issue.
  A dependency cycle or a provider that depends on a deeper-scoped one can only
  ever be *introduced* by more registration, never fixed by it — so `validate`'s
  default `True` now raises those from `Container(...)` itself, before you get
  a chance to use a broken graph. Missing dependencies and dangling aliases are
  the opposite: registering more providers can complete them, so those two
  stay held until first use, which is what keeps a framework integration's
  "register providers after construction" pattern working.

## Why

Six days after 3.0 shipped, field evidence pointed at one root cause behind
six separate production defects: an integration's root container is opened in
one place, but some execution contexts (a non-prefork worker pool, a mounted
sub-app, a disabled lifespan hook) never reach that code path, so the very
first unit of work in that context raised. Binding validation to `open()` also
created an authoring trap — a caller had to open the root *after* registering
its providers, or a by-type dependency on a not-yet-registered connection
failed validation early. Both problems are structural consequences of making
`open()` load-bearing, not bugs in any particular integration. 3.1 removes the
load-bearing requirement while keeping the diagnostic value: a broken graph
still fails fast, just from the constructor for the errors that can only get
worse, and at first use for the ones that can still resolve themselves.

## Deprecation

- **`ContainerClosedError` is inert.** Nothing raises it anymore; it stays
  importable and documented through the 3.x series and is removed in 4.0. If
  you catch it explicitly, that code path is now dead — safe to leave in place
  or remove.
- **Want 3.0's strictness back?** Run with
  `-W error::modern_di.exceptions.ContainerClosedWarning` (or the pytest
  `filterwarnings` equivalent) to turn a closed-container reuse back into a
  hard failure. This is the one 3.0 behavior that has no other way back —
  everything else in this release is additive.

## Downstream

No action needed for `modern-di-*` integrations (aiohttp, FastAPI, FastStream,
Litestar, Starlette, Typer, Flask, gRPC, Celery, arq, taskiq, aiogram) or
`modern-di-pytest` — every 3.0-era `open()`/`with` call site keeps its exact
meaning. Upgrading is a drop-in floor bump.

## Internals

- 100% line coverage maintained across Python 3.10–3.14; `ruff` and `ty` clean;
  docs built under `mkdocs --strict` in CI.
- Construction-time cost moves, not doubles, for the common case: a container
  that constructs and then opens pays roughly the same total work as 3.0, just
  split differently between the two calls. The one case that gets more
  expensive is a `validate=True` (the default) container that is constructed
  and never opened — it now pays upfront, at `__init__`, for a graph walk 3.0
  deferred until you called `open()` or resolved something.
